# AGENTS.md

Operating manual for **any** AI coding agent (Claude Code, Codex, Cursor, OpenCode, etc.) working on the RepoHeart repository.

`CLAUDE.md` tells you the **architecture rules** (what the code must be). This file tells you the **workflow rules** (how to actually work in the repo — branches, commits, PRs, and where everything lives). Read both before touching anything.

> If any instruction here conflicts with a maintainer's explicit request in an issue or task, ask before proceeding. When in doubt, do less and escalate.

---

## 1. Orientation — Read These First

Before starting a task, load context in this order:

| Order | File | Why |
|---|---|---|
| 1 | `PROJECT.md` | What RepoHeart is, principles, status. |
| 2 | `CLAUDE.md` | The seven non-negotiable architecture invariants. |
| 3 | `ARCHITECTURE.md` | Component map, interfaces, request lifecycle. |
| 4 | `docs/repoheart-final-system-design.md` | The authoritative full spec. **If code and this doc disagree, the doc wins.** |
| 5 | `ROADMAP.md` | Which phase we're in and what's in scope now. |
| 6 | `CONTRIBUTING.md` | Dev setup, conventions, test requirements. |

Do not start writing code until you can state, in one sentence, which component your change belongs to and which roadmap phase it serves.

## 2. The Golden Rules (never violate)

These come from `CLAUDE.md` — repeated here because they gate every task:

1. **Stateless between runs** — no required database.
2. **Agents never execute writes** — `run()` returns declarative actions; only Orchestrator + Safety Gate execute.
3. **No write bypasses the Safety Gate.**
4. **Deterministic core** — no LLM in routing, safety, idempotency, retrieval orchestration.
5. **Provider-agnostic agents** — no provider SDK imports inside agents.
6. **Safety invariants** — no self-escalation, no force-push, no merge capability, no committed secrets.
7. **Bounded per event** — respect `ContextBudget` and per-run ceilings.

If a task appears to require breaking one of these, **stop and open an issue describing the conflict** instead of working around it.

## 3. Task Workflow (start to finish)

```text
1. Understand the task     → read the issue; confirm scope + phase
2. Sync main               → git switch main && git pull --ff-only
3. Create a branch         → see §4 naming rules
4. Make the change         → smallest change that solves it (§6)
5. Test                    → add/adjust tests; run the full gate (§7)
6. Self-review             → run the PR checklist (§9)
7. Commit                  → Conventional Commits (§5)
8. Push + open PR          → fill the PR template (§8)
9. Respond to review       → address feedback, keep commits clean
```

Never commit directly to `main`. Never push to `main`. Every change goes through a branch and a PR.

## 4. Branch Naming

Task-based, kebab-case, prefixed by type. **Never** name a branch after yourself, the AI tool, a timestamp, or a random suffix.

```text
<type>/<short-task-description>
```

Allowed types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `ci`.

**Good:**
```text
feat/issue-triage-agent
fix/rate-limit-backoff
refactor/safety-gate-decision-token
docs/config-reference
test/conflict-resolution-escalation
```

**Not allowed:**
```text
claude/my-work
codex/patch-1
cursor-branch
himanshu-fixes
update-2026-08-24
tmp
```

If an issue number applies, you may append it: `feat/issue-triage-agent-42`.

## 5. Commit Messages — Conventional Commits

Format:

```text
<type>(<optional scope>): <imperative summary>

<optional body: what & why, not how>

<optional footer: Closes #123>
```

Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`, `ci`, `build`.

Rules:
- Imperative mood: "add", not "added"/"adds".
- Summary ≤ 72 chars, no trailing period.
- Scope = the component when useful: `agents`, `safety`, `providers`, `retrieval`, `router`, `config`, etc.
- One logical change per commit. Don't bundle unrelated edits.
- Reference issues in the footer: `Closes #42`, `Refs #42`.

**Good:**
```text
feat(agents): add issue triage classification and labeling
fix(github-ops): honor Retry-After on secondary rate limits
test(safety): assert no MERGE action can be produced
docs(readme): document provider switching
refactor(safety): require Decision token in git write methods
```

**Not allowed:**
```text
update stuff
wip
fixes
final commit
Generated by Claude
```

### Authorship & attribution — important

- Commit as the **human contributor's** git identity. Do **not** set an AI as author.
- **Do not add AI attribution footers or co-author trailers.** No `Generated by Claude`, no `Co-Authored-By: Claude <...>`, no tool signatures. Commits must look like ordinary human commits.

## 6. Change Scope — Minimal Changes

RepoHeart itself follows a "minimal change" principle; so must you when editing it.

- Make the **smallest change** that fully solves the task.
- Don't refactor unrelated code "while you're in there." If you spot separate issues, note them for a follow-up, don't fold them in.
- Don't reformat files you didn't functionally change.
- Put code in the component that owns the concern (see the layout below). Don't spread one concern across layers.
- Prefer feeding the LLM **tool output** (linters, tests, search, symbol graphs) over raw whole files — this is a product principle, apply it in the code you write too.

### Where things go

```text
repoheart/
├── config/         repoheart.yml schema + loader
├── events/         context builder, event types, router
├── orchestrator/   sequencing, agent context, budgets
├── agents/         one file per agent (base.py = ABC)
├── retrieval/      structural/lexical/semantic + chunking + budget
├── repo_access/    sparse/shallow/partial checkout, merge-base
├── cache/          optional cache backends
├── providers/      one file per provider (base.py = ABC)
├── git_ops/        local git operations
├── github_ops/     GitHub API wrappers + rate budgeter
├── safety/         policy table + gate
├── idempotency/    fingerprint + markers
└── observability/  structured logger
```

## 7. The Test Gate (must pass before commit)

```bash
ruff check .          # lint
mypy repoheart        # type check
pytest                # tests
```

All three green, every time. Additional requirements:

- **Every agent** needs a test feeding a synthetic event and asserting its `ProposedAction`s.
- **Every agent test** must assert no proposed action exceeds the agent's risk ceiling.
- **Every safety invariant** needs a test that would fail if the invariant were broken (e.g. no `MERGE` action producible; force-push never issued; low-confidence conflict escalates).
- **Mock the provider** — never call a real LLM in unit tests.
- Run locally against a saved payload when relevant:
  ```bash
  python -m repoheart.main --event examples/issues.opened.json --config repoheart.yml
  ```

If you add or change behavior, config, or routing, update the docs in the same PR.

## 8. Pull Requests

- One PR = one focused change tied to one task/issue.
- Title uses Conventional-Commit style: `feat(agents): add duplicate detection`.
- Description must cover: **what** changed, **why**, which **component**/phase, and how it was **tested**.
- Link the issue: `Closes #NN`.
- Keep the branch rebased on current `main`; resolve conflicts locally (never force-push a shared branch — for your own PR branch, prefer `--force-with-lease` only if truly needed and never on `main`).
- Do not merge your own PR unless a maintainer says so. RepoHeart's own repo requires human review to merge — same philosophy the product enforces.

- [ ] Safety-relevant change has a regression test

## 10. Recipes

### Adding an agent
1. Subclass `Agent` in `agents/<name>.py` — set `name`, `risk_level` (ceiling), `handles_events`.
2. Implement `run(context) -> AgentResult`. No direct writes.
3. Register event types in `events/router.py`.
4. Add config toggle to the schema + `repoheart.schema.json`.
5. Add tests (proposed actions + risk ceiling, mocked provider).
6. Update roster + routing table in `docs/repoheart-final-system-design.md`.

### Adding a provider
1. Subclass `Provider` in `providers/<name>.py`; implement `complete()` + `supports_tools()`.
2. Register in the provider registry; add to the config `provider.name` enum.
3. Add credential env var to `action.yml` and the workflow template.
4. Add a smoke test with recorded/mocked responses.
5. Never leak provider specifics above the `Provider` interface.

## 11. Hard "Do Not" List

- Do **not** commit or push to `main`.
- Do **not** force-push `main` — ever.
- Do **not** add AI attribution / co-author footers to commits.
- Do **not** name branches after tools, people, dates, or random strings.
- Do **not** add Redis/Postgres as a requirement.
- Do **not** let an agent call `github_ops`/`git_ops` write methods directly.
- Do **not** add a merge capability.
- Do **not** commit secrets, tokens, or credentials — check your diff before every commit.
- Do **not** default to full-history clone (`fetch-depth: 0`).
- Do **not** silently diverge from the final design doc — change the doc deliberately if the design must change.
- Do **not** bundle unrelated changes into one PR.

## 13. Release Workflow

Follow this sequence **in order** every time a version is shipped to PyPI. Do not skip steps.

### Step 1 — Decide the version bump

Follow [Semantic Versioning](https://semver.org/). Use the versioning rules in `CHANGELOG.md`:

| Change type | Bump |
|---|---|
| Breaking change to `repoheart.yml` schema, `Agent` ABC, or `Provider` ABC | **MAJOR** |
| New agent, provider, or backward-compatible feature | **MINOR** |
| Bug fix or safe internal improvement | **PATCH** |

### Step 2 — Update `pyproject.toml`

Edit the `version` field:

```toml
[project]
version = "X.Y.Z"   # new version, no leading v
```

### Step 3 — Update `CHANGELOG.md`

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/) format.

1. Replace `## [Unreleased]` with the new version heading:
   ```markdown
   ## [X.Y.Z] - YYYY-MM-DD
   ```
2. Add a fresh `## [Unreleased]` block above it (always keep this header):
   ```markdown
   ## [Unreleased]

   ---

   ## [X.Y.Z] - YYYY-MM-DD
   ```
3. Write release notes under `### Added`, `### Changed`, `### Fixed`, `### Removed`, `### Security` as applicable. Every user-visible change must appear.
4. Update the diff links at the bottom of the file:
   ```markdown
   [Unreleased]: https://github.com/OpenAgentHQ/repoheart/compare/vX.Y.Z...HEAD
   [X.Y.Z]: https://github.com/OpenAgentHQ/repoheart/compare/vPREV...vX.Y.Z
   ```

### Step 4 — Run the full test gate

```bash
ruff check .
mypy repoheart
pytest
```

All three must be green before committing.

### Step 5 — Commit the release prep

Use a single, focused commit. No other changes mixed in.

```bash
git add pyproject.toml CHANGELOG.md
git commit -m "chore(release): bump version to vX.Y.Z"
```

### Step 6 — Create and push an annotated tag

Tags must be annotated (not lightweight) and use the `vX.Y.Z` format.

```bash
git tag -a vX.Y.Z -m "Release vX.Y.Z"
git push origin main
git push origin vX.Y.Z
```

### Step 7 — Create and publish a GitHub Release

> **This is the step that triggers the PyPI upload.** `publish.yml` fires on
> `release: types: [published]` — only when a GitHub Release is published, not
> on a raw tag push. Pushing a tag alone does **not** publish to PyPI.

1. Go to **GitHub → Releases → Draft a new release**.
2. Select the tag `vX.Y.Z` you just pushed.
3. Set the title to `vX.Y.Z`.
4. Paste the `CHANGELOG.md` section for this version into the description.
5. Click **Publish release**.

`publish.yml` will now run automatically:
- `build` job: checks out the tag, builds wheel + sdist via `hatch build`
- `publish` job: uploads `dist/` to PyPI via OIDC trusted publishing (no API token required)

> **One-time PyPI setup** (if not already done): add a trusted publisher at
> pypi.org → Your account → Publishing → Add a new pending publisher.
> Set: project `repoheart`, owner `OpenAgentHQ`, repo `repo-heart`,
> workflow `publish.yml`, environment `pypi`.

### Step 8 — Verify the release

- Check the **Actions** tab: both `build` and `publish` jobs must be green.
- Confirm the new version is live: `pip install repoheart==X.Y.Z`
- Test the installed CLI: `repoheart --version`

## 14. When to Stop and Ask

Escalate to a human (comment on the issue/PR, don't guess) when:

- The task seems to require breaking a golden rule.
- The design doc and the requested behavior conflict.
- A change touches the Safety Gate, permission model, or Git safety and you're not fully certain it's correct.
- You'd need to introduce required external infrastructure.
- Tests can't be written to cover a safety-relevant change.

> Same principle RepoHeart applies to repositories, applied to yourself: **safety first, then correctness, then automation. When confidence is low — stop, explain, ask.**
